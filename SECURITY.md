# Модель безопасности — «Платежи ITnimax»

Документ описывает архитектуру безопасности, поверхность атаки и меры защиты.
Он честный: закрытые вопросы отмечены ✅, открытые — ⬜ с планом.

## 1. Что за система и какие данные

Внутренний сервис бухгалтерской аутсорсинговой компании: клиент по персональной
ссылке оставляет заявку на платёж, бухгалтер ведёт единую очередь.

**Классификация данных:**
- **Персональных данных (ПДн) физлиц — НЕТ.** Хранятся платёжные поручения:
  получатель, сумма, УНП (налоговый номер **компании**, не физлица), назначение,
  необязательно файл счёта.
- Данные **коммерчески чувствительные**, но не подпадают под 152-ФЗ/GDPR как ПДн.
- Вывод: обязательств по хранению ПДн, ради которых иногда требуют собственный
  сервер, здесь нет.

## 2. Архитектура и границы доверия

```
Клиент/бухгалтер ── HTTPS ──> GitHub Pages (статика, за CDN Fastly)
                                    │  JS вызывает Supabase
                                    ▼
                         Supabase (за Cloudflare)
                    ┌───────────────┼────────────────┐
              PostgreSQL+RLS   Auth (JWT)   Edge Functions (service_role)
                                                 │
                                          Telegram Bot API
```

- **Фронтенд** — статические файлы, секретов не содержит (кроме публичного
  anon-ключа, которому положено быть публичным).
- **Бэкенд** — managed PostgreSQL. Прямой доступ к таблицам закрыт, клиент ходит
  только через функции (RPC).
- **Edge Functions** — серверный код, работает с `service_role` (обходит RLS),
  недоступен клиенту.

## 3. Роли и доступ

| Актор | Аутентификация | Что может |
|-------|----------------|-----------|
| **Клиент** | персональный токен в ссылке `?t=<token>` (128-бит hex) | вызвать только RPC своей заявки: `client_by_token`, `list_payments_by_token`, `submit_payment`, `edit_payment_by_token`. К таблицам напрямую доступа нет |
| **Бухгалтер** | Supabase Auth (email+пароль, JWT) | видит платежи только своих клиентов (RLS) |
| **Админ** | Supabase Auth + `is_admin()` | видит всё, заводит клиентов/бухгалтеров, читает audit log |
| **Edge Functions** | `service_role` (серверный секрет) | системные операции: уведомления, бот |

## 4. Меры защиты (что уже есть) ✅

- **RLS включён** на `payments`, `clients`, `staff`, `tg_sessions`, `payments_audit`.
- **anon отозван** от прямого доступа к `payments` и `payments_audit` (`revoke all`)
  — клиент физически не может читать таблицы, только через SECURITY DEFINER-функции,
  которые сами проверяют владение по токену.
- **HTTPS везде** — и GitHub Pages (Fastly), и Supabase (Cloudflare).
- **Секреты не в git и не во фронте:** токен бота, `service_role`, webhook-секрет —
  в репозитории плейсхолдеры, реальные значения только в проде. anon-ключ публичен
  by design (при включённом RLS сам по себе ничего не открывает).
- **Storage:** путь файла — 128-битный случайный (`crypto.getRandomValues`), публичный
  URL невозможно угадать или перечислить.
- **Telegram webhook** защищён секретным заголовком (`TG_WEBHOOK_SECRET`).
- **Параметризованные запросы** в RPC — SQL-инъекции исключены (нет конкатенации SQL).
- **Rate-limiting** на anon-RPC (фиксированное окно в БД): `submit_payment` —
  10/мин и 60/час на токен, `edit_payment_by_token` — 20/мин. Служебная таблица
  счётчиков недоступна anon/authenticated.
- **Audit log** — журнал смены статусов платежей (кто/когда/из чего в что).
- **Тесты изоляции** — pgTAP в CI проверяют, что клиент А не видит платежи Б и что
  anon не имеет прямого доступа к таблицам.

## 5. Поверхность атаки и риски

### 5.1 Токен в URL ✅ (митигировано)
Ссылка `?t=<token>` = пароль клиента. Может утечь через историю браузера,
пересылку, скриншот, referrer.
- **Защита:** токен 128 бит (перебор невозможен), доступ только к данным одного
  клиента, RLS. **Ротация:** админ перевыпускает ссылку одной кнопкой
  (`rotate_client_token`) — утёкший токен мгновенно мёртв.
- **Остаточный риск:** окно между утечкой и отзывом.

### 5.2 Anon-поверхность RPC ✅ (митигировано)
`submit_payment` / `edit_payment_by_token` вызываемы любым, у кого есть валидный токен.
- **Защита:** требуется токен, проверка владения, статус-гейт (правка только `new`),
  **rate-limiting на уровне БД**: submit — 10/мин и 60/час, edit — 20/мин на токен.
  Лимит в БД, поэтому покрывает оба канала (веб и Telegram-бот).
- **Остаточный риск:** злоупотребление в пределах лимита; видно в audit log.

Отдельно закрыт **избыточный доступ анонима к служебным RPC** (09.08.2026).
PostgreSQL выдаёт `EXECUTE` новой функции роли PUBLIC, а Supabase — ещё и `anon`,
поэтому `grant execute … to authenticated` ничего не ограничивал: аноним с
публичным ключом мог вызвать `rotate_client_token`, `delete_client` и
`send_daily_reminder`.
- **Эксплуатируемость:** у первых двух внутри гейт `is_admin()` — для анонима
  ложный, то есть данные были недоступны. У `send_daily_reminder` гейта нет:
  можно было повторно рассылать бухгалтерам утренний список (спам уведомлениями).
- **Защита:** явный `revoke all … from public, anon` (миграция
  `20260809000002_lock_admin_rpc.sql`). Проверяется тестами, включая обратную
  страховку: функции клиента по токену обязаны остаться доступными `anon`.

### 5.3 DDoS
- **Фронтенд** за Fastly (GitHub Pages), **API** за Cloudflare — промышленная защита
  от DDoS. Это **устойчивее собственного сервера**, а не слабее.
- Уязвимая вычислительная поверхность — Edge Functions и RPC; злоупотребление
  частотой закрывается rate-limiting (п.4).

### 5.4 Утечка токена бота
- В публичный репозиторий не попадает (плейсхолдеры). При утечке — злоупотребление
  ботом; **митигация:** ротация токена у @BotFather.

### 5.5 Storage
- Бакет публичный (нужно для ссылок в Telegram), но пути случайные и не листингуются.
  Доступ только по знанию точного URL.

## 6. Соответствие требованиям
- ПДн физлиц не обрабатываются → обязательства 152-ФЗ/GDPR по ПДн практически не
  применимы. Применима коммерческая тайна (доступ ограничен ролями).

## 7. Открытые задачи (роадмап безопасности)
- ✅ Rate-limiting на RPC (п.4) — 10/мин, 60/час на submit; 20/мин на edit
- ✅ Отзыв/ротация токенов клиента (п.5) — кнопка «Перевыпустить»
- ✅ Автобэкапы (п.6) — ежедневный шифрованный дамп в GitHub Actions
- ⬜ Мониторинг/алерты (п.7)
- ⬜ RUNBOOK по инцидентам и восстановлению (п.9)

## 8. Реагирование на инцидент (кратко; подробно — в RUNBOOK)
- **Утёк токен клиента:** перевыпустить токен клиента в БД → старая ссылка мертва.
- **Утёк токен бота:** `/revoke` у @BotFather → обновить секрет функций.
- **Утёк `service_role`/JWT:** ротация ключей в Supabase → редеплой функций.
- **Порча данных:** откат к тегу `v2.1-pilot-ok` (фронт) + восстановление из бэкапа (БД).
