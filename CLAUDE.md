# CLAUDE.md — как работать с этим проектом

Правила и грабли, специфичные для «Платежей под контролем». Общие принципы
хорошего кода тут не повторяются — только то, что вытекает из устройства
этого проекта и на чём мы уже спотыкались.

Устройство системы — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).
Эксплуатация и инциденты — [docs/RUNBOOK.md](docs/RUNBOOK.md).
Модель угроз — [SECURITY.md](SECURITY.md).

---

## ⚠️ Система живая

Ей пользуются **реальные клиенты и бухгалтеры прямо сейчас**. Ошибка здесь —
это потерянное или продублированное платёжное поручение.

- Любое изменение сначала обкатывается **локально** (`supabase start`), и только
  потом идёт на прод.
- После деплоя изменения обязательно **проверить фактом**, а не выводом команды:
  запросить прод дампом, дёрнуть эндпоинт, посмотреть реальный ответ.
- Деплой и миграции на прод — только с явного согласия пользователя.

## Бэкенд — только через миграции

Схема, RPC и политики живут в `supabase/migrations/`. Менять их кликами в панели
Supabase **нельзя**: изменение потеряется и разъедется с кодом.

```
новый файл supabase/migrations/ГГГГММДДЧЧММСС_описание.sql
  → supabase db reset      (пересобрать локально с нуля)
  → supabase test db       (290 тестов, должны быть зелёными)
```

Миграции **аддитивные**: добавляют колонки/таблицы/функции. Откат — компенсирующей
миграцией, а не правкой старого файла. `db reset` **никогда** против прода.

## Порядок деплоя (нарушать нельзя)

```
1. supabase db push              миграции
2. supabase functions deploy …   Edge Functions
3. git push                      фронт → GitHub Pages
```

Фронт последним: он вызывает то, чего до миграции в базе ещё нет. Обратный
порядок = ошибки у живых клиентов.

`git push` сайт сразу не выкатывает: `deploy.yml` сначала гоняет тесты и
сторожа секретов и публикует только при зелёных (M11.4, 5–7 минут). Красный
CI = сайт остался прежним. Не обходить — чинить.

## Четыре места, где легко всё сломать

**1. Добавление параметра к RPC — это перегрузка, а не замена.**
`create or replace function` с новым аргументом создаёт ВТОРУЮ функцию, и вызов
со старым числом аргументов падает с «function ... is not unique». Старую версию
надо удалять явно:
```sql
drop function if exists public.имя(старый, список, типов);
```
После пересоздания **права не переезжают** — `grant execute` выдавать заново,
иначе клиенты по токену встанут. Проверяется в `security_surface_test.sql`.

Параметр добавляй со значением по умолчанию: между накатом миграции и выкладкой
фронта живой прод вызывает функцию по-старому, и этот вызов обязан работать.

**2. Baseline-миграция содержит плейсхолдер токена.**
`send_daily_reminder` в проде хранит реальный токен внутри тела, а в
`20260622000000_baseline.sql` стоит `<TELEGRAM_BOT_TOKEN>`. Прогнать baseline на
проде = сломать утренние уведомления. Он помечен применённым через
`supabase migration repair` — не «переприменять».

По той же причине **текст рассылки вынесен из этой функции**: собирает его
`daily_reminder_message()` из миграции, а за `send_daily_reminder` осталась
оболочка «взять текст и разослать». Значит: меняешь ТЕКСТ — обычной миграцией,
как всё остальное; меняешь оболочку — только руками из
`supabase/daily_reminder.sql`, подставив токен, и это единственное место в
проекте, где прод расходится с репозиторием намеренно.

**3. Новый объект в БД по умолчанию открыт анониму.**
PostgreSQL выдаёт `EXECUTE` на новую функцию роли PUBLIC, а Supabase вдобавок
раздаёт права `anon` и `authenticated`. Значит `grant execute … to authenticated`
**ничего не ограничивает** — оно лишь дублирует уже выданное. Служебную или
админскую функцию нужно закрывать явно:
```sql
revoke all on function public.имя(типы) from public, anon;
grant execute on function public.имя(типы) to authenticated;
```
Ровно так же в своё время оказалась открыта таблица `payments_audit`.

С таблицами то же самое: свежий образ Supabase выдаёт `anon` права ALL на
каждую новую таблицу в `public`. С 16.09 миграция
`20260916000002_revoke_anon_tables.sql` меняет default privileges, но
полагаться на это при новой таблице не стоит — проверяй
`has_table_privilege('anon', …)` в тесте. Этот класс ошибок три недели держал
CI красным, пока у разработчика стоял старый CLI и всё было зелёным: **версия
CLI в CI и локально должна совпадать** (закреплена в `test.yml`).
Проверяется в `security_surface_test.sql` — там же страховка от обратной
ошибки: клиентские функции по токену обязаны остаться доступными `anon`.

**4. Секреты в репозиторий не попадают.**
В файлах только плейсхолдеры, реальные значения — в Supabase Secrets и GitHub
Secrets. Дамп прода содержит боевые токены: не класть его в репозиторий и удалять
после проверки.

## Запись в очередь — только точечная

Здесь был общий `save()`: upsert **всех** заявок из состояния вкладки на каждое
нажатие. Побеждал тот, кто нажал последним, и это давало сразу пять находок
ревью — от отката чужих статусов (риск оплатить дважды) до ложного «бухгалтер
изменил вашу заявку» клиенту.

Правило, которое пришло ему на смену:

- пишем **ровно те поля**, которые человек менял. Смена статуса не трогает
  содержание, правка содержания не трогает статус (`updateContentRemote`);
- пишем **в одну строку**, а не во все (`insertPaymentRemote` вместо upsert
  очереди);
- переход статуса идёт с условием `.eq("status", <что человек видел>)`. Не
  совпало — значит заявку тронули, пока он смотрел: **перечитать и сказать
  ему**, а не записать поверх (`changeStatusRemote`, `attachDocRemote`);
- никакого «тихо не получилось»: удаление и вставка ждутся и проверяются.

Добавляешь новое действие в очередь — оно обязано лечь в эту же схему.
Проверяется `node tools/racecheck.mjs`: он воспроизводит гонку двух вкладок
целиком, включая доказательство, что старый upsert действительно откатывал
чужую отметку.

## Уведомления: ничего не теряем молча

`notify-client` разбирает четыре повода — документ, переписка, статус, правка —
и раньше каждый заканчивался `return`. Первая сработавшая ветка отменяла
остальные: клиент без Telegram или битая ссылка на документ делали заявку
глухой навсегда. Правила теперь такие:

- **ветка не выходит из функции.** Сделала своё дело — дописала в `patch` и
  `done`, а строка обновляется один раз в конце. Добавляешь пятый повод —
  добавляй так же;
- **отправка не имеет права бросать.** `fetch` при сетевой ошибке кидает
  исключение, а не возвращает `!ok`; необёрнутый `fetch` в ветке рубит весь
  вызов. Внутри `tg` и `tgDocument` оба случая уже закрыты — шли через них;
- **каждая осечка пишется в `notify_failures`** (ветка, заявка, чат, ответ
  Telegram). У Database Webhooks нет ретраев, и `console.error` никто не читает:
  именно так вышел инцидент «клиент месяц без уведомлений». Сторожит счётчик
  `health.yml` через `notify_failures_recent` — она отдаёт только число, поэтому
  её можно звать публичным ключом;
- **что доставлено — то записано**, в том числе если дальше вылетело
  исключение. Иначе счётчики останутся на месте и клиент получит те же
  сообщения повторно;
- **секреты читать через `?? ""`, а не `!`.** Восклицательный знак — обещание
  компилятору, а не проверка: `notify-payment` из-за него падала на импорте,
  не успевая записать отказ.

**Уведомления сотрудникам адресные — так же, как очередь.** Бухгалтер получает
только своих клиентов (`clients.staff_id`), админ — всех; клиент без бухгалтера
— админу; бухгалтер без `telegram_id` — админу плюс запись в `notify_failures`.
До 14.09 «новая заявка», «клиент ответил» и «клиент изменил» уходили всем
номерам из секрета `TELEGRAM_CHAT_ID`, и с третьим бухгалтером это стало общей
корзиной.

- Правило живёт **в базе**, в одном месте: `notify_staff_chats(client_id)` для
  мгновенных уведомлений и `daily_reminder_message(staff_id)` для утреннего
  письма. Функции только зовут RPC. Добавляешь новое уведомление сотрудникам —
  бери адресатов оттуда же, не заводи свой список;
- номера сотрудников — **только** `staff.telegram_id`. Секрет `TELEGRAM_CHAT_ID`
  функциями больше не читается: второе место для номеров уже однажды
  разъехалось с первым (M4.6);
- личная задача (`client_id is null`) — только автору, в том числе админу не
  приходят чужие личные задачи в утреннем письме;
- проверяется `addressed_notifications_test.sql`. Тест «и больше никому» держит
  в фикстуре бухгалтера с Telegram, но без клиентов — без него сломанное
  правило «слать всем» случайно давало правильный ответ.

## Локальная разработка: грабли Windows

| Что | Как правильно |
|---|---|
| `supabase` не найден | `$env:Path = "$env:USERPROFILE\scoop\shims;$env:Path"` |
| `docker` не найден | полный путь `C:\Program Files\Docker\Docker\resources\bin\docker.exe` |
| `bash` в PowerShell | уходит в WSL без дистрибутива → `& "C:\Program Files\Git\bin\bash.exe"` |
| Порты стека | сейчас `183xx`. Windows раздаёт динамические порты по всему диапазону, и Hyper-V периодически резервирует новый кусок — стек перестаёт стартовать. Свободное искать через `netsh interface ipv4 show excludedportrange protocol=tcp` и двигать порты в `config.toml` |
| SQL с кириллицей в контейнер | **не** `Get-Content \| docker exec` (PowerShell портит кодировку) — либо `supabase db reset`, либо `docker exec -i psql < file` из Git Bash |
| `docker cp` из Git Bash | ломает путь внутрь контейнера → подавать файл через stdin |
| `Get-Content` в PowerShell 5.1 | без `-Encoding utf8` читает файл как ANSI и превращает кириллицу в мусор. Собирать файлы `cat`-ом из Git Bash, а не склейкой в PowerShell |
| Большой heredoc в Bash | на файле в сотни строк рвётся на кавычках — писать инструментом записи файла, а не `cat <<EOF` |
| `python` | это заглушка Microsoft Store, а не интерпретатор: падает с кодом 49. Настоящего Python нет |

## Вёрстка и PDF: чем смотреть результат

Проверять глазами, а не по коду: на вёрстке уже дважды ловили баги, которые из
исходника не видны.

- **Скриншот страницы** — headless Chrome:
  `chrome.exe --headless=new --disable-gpu --no-sandbox --hide-scrollbars --window-size=W,H --virtual-time-budget=15000 --screenshot=out.png file:///…`
  Окно **не бывает уже 485 css-пикселей**: снимок в 390 просто обрежет картинку,
  и это легко принять за поломку вёрстки. Настоящую ширину проверять скриптом
  (`document.documentElement.scrollWidth`) через `--dump-dom`, а не на глаз.
  Всплывашки на `position:fixed`, появившиеся по таймеру, в снимок не попадают —
  проверять их тоже через `--dump-dom`.
- **PDF из HTML** — тот же Chrome с `--print-to-pdf=out.pdf --no-pdf-header-footer`.
  Фоны он по умолчанию **не печатает**: без `print-color-adjust: exact` от
  оформления останется голый текст.
- **Посмотреть страницы готового PDF** — poppler и ImageMagick не установлены,
  но есть встроенный в Windows `Windows.Data.Pdf`: из PowerShell грузим
  `PdfDocument.LoadFromFileAsync` и рендерим `RenderToStreamAsync` в PNG.
  Ставить ничего не нужно.
- **Печатная палитра проигрывает тёмной теме по специфичности:** у
  `:root:not([data-theme="light"])` вес выше, чем у простого `:root`, поэтому в
  `@media print` перечислять те же селекторы. Первый PDF руководства из-за этого
  вышел целиком тёмным.
- **Полоса A4 — это 688 css-пикселей**, то есть в печати срабатывают мобильные
  медиазапросы. Таблицы, свёрнутые в один столбец «для телефона», надо возвращать
  в печатных стилях явно.

## Даты и рабочий график

Бухгалтерия работает **пн–пт до 17:00 (Europe/Minsk)**. Правило живёт в БД
(`adjust_due_date`), поэтому одинаково действует в вебе и в боте:
будущий выходной → ошибка; «сегодня» в нерабочее время → перенос на следующий
рабочий день; прошлые даты не трогаем.

Из этого следует:
- **не использовать жёсткие относительные даты** (`current_date + 2`) в сидах и
  тестах — они попадают на выходные и роняют сид вместе с `supabase start` и CI.
  Брать `next_working_day(...)`;
- время проверяемых сценариев передавать явно: `adjust_due_date(date, timestamp)`
  существует именно для тестируемости;
- даты на фронте собирать через `isoLocal`, **не** `toISOString` — иначе в поясе
  РБ получается «вчера».

## Тесты

pgTAP в `supabase/tests/`, запуск `supabase test db`, сейчас **290 тестов**.
Гоняются в CI на каждый push.

Edge Functions тестами почти не покрыты — исключение
`supabase/functions/telegram-bot/bind_test.sh` (привязка `/start`, запускается
вручную против локально поднятой функции, инструкция в шапке файла). Он появился
после боевого инцидента: клиент почти месяц не получал уведомления, потому что
неудачная привязка стирала прежнюю. Меняешь `/start` — прогони его.

Тест должен доказывать поведение, а не факт «не упало»: проверять записанные
значения, а не только отсутствие исключения. Если сомневаешься в ценности теста —
сломай проверяемое место намеренно и убедись, что тест краснеет.

Особенности pgTAP здесь:
- `isnt(:'var', 'lit')` падает на выводе полиморфного типа → нужен `::text`;
- сортировать записи журнала по `id`, а не по `changed_at`: внутри транзакции
  `now()` одинаков у всех строк;
- `staff.id` ссылается на `auth.users` → в тестах сначала `insert into auth.users (id)`.

## Предметная область

- Валюта — **Br** (белорусский рубль), реквизиты — **УНП** (не ИНН).
- Статусы платежа: `new → in_progress → paid → sent`.
- Клиент ходит только через RPC по токену; прямого доступа к таблицам у `anon` нет.
- Уведомление клиенту «оплачено» уходит **ровно один раз** (флаги на платеже).
- Заявки, созданные бухгалтером, клиент видит, но не редактирует.
- Файлы лежат в массиве `payments.files`. Колонки `file_url` / `file_name`
  остались **зеркалом первого файла** — их читают утренняя рассылка,
  `notify-payment` и бот. Меняешь файлы — обновляй зеркало, иначе вложение
  молча пропадёт из уведомлений (проверяется в `multi_files_test.sql`).
- **Ссылка на файл — только `http(s)`.** Она уходит в `href`, и `javascript:`
  в ней выполнялся бы в сессии бухгалтера при клике по скрепке; `esc()` от
  этого не спасает, он экранирует кавычки, а не схему. Проверка одна на всех —
  `is_safe_file_url` — и стоит в трёх дверях, через которые файл попадает в
  заявку: `normalize_files` (подача и правка клиентом) и `reply_by_token`
  (ответ в переписке). Добавляешь четвёртую дверь — ставь туда же.
  Во фронте зеркало этой проверки — `safeUrl()` в `app/js/utils.js`: она
  прикрывает записи, заведённые до проверки, и `staff_files`, которые пишутся
  напрямую в таблицу, минуя RPC. Проверяется в `url_scheme_test.sql`.
- **Всё, что уходит в Telegram, экранируется.** Сообщения шлются с
  `parse_mode: HTML`, а `payee`, `purpose`, `requisites` пишет клиент. В
  функциях helper зовётся `esc()`, в базе — `tg_esc()`. Забыл — сообщение
  разваливается или подменяется чужой разметкой.
- Бакет `files` принимает **до 10 МБ** и только типы из белого списка. Список
  продублирован в трёх местах, и они обязаны сходиться: миграция
  `20260826000003_storage_limits.sql` (единственная настоящая проверка),
  `MIME_BY_EXT` в `app/js/supabase.js` и `MIME_BY_EXT` в боте — последние два
  нужны, чтобы человек увидел причину отказа, а не «файл не загрузился», и
  чтобы бакет получил тип явно: для heic на Windows браузер отдаёт пустой
  `file.type`, и бакет отвергал годный файл (M3.2).
  Добавляешь тип — правь все три, иначе фронт пропустит файл, который отвергнет
  бакет. Лимиты бакета действуют и на `service_role`: бот под них тоже попадает,
  подписать файл `application/octet-stream` в обход больше нельзя.
- **Один Telegram-аккаунт может быть привязан к нескольким фирмам.** Человек
  ведёт две компании — обе шлют ему уведомления. `clients.telegram_id` не
  уникален, и `/start` прежние привязки **не снимает** (снимал раньше — из-за
  этого человек с двумя фирмами не мог получать уведомления по обеим).
  Отсюда правило: **искать клиента по `telegram_id` через `.maybeSingle()`
  нельзя** — на двух строках он вернёт ошибку, и бот ответит «вы ещё не
  привязаны». Брать список (`getClients` в боте). Диалог заведения заявки
  требует ровно одной фирмы: при нескольких бот отправляет человека на
  персональную ссылку, иначе заявка уйдёт не на ту компанию. Отвязать фирму
  можно перевыпуском её ссылки (`rotate_client_token` сбрасывает `telegram_id`).
  Проверяется в `bind_test.sh` и `delete_client_test.sql`.
- **Документы бухгалтера лежат в `payments.staff_files`, отдельно от `files`.**
  `files` — счёт ОТ клиента, и его первый элемент зеркалится в `file_url`,
  который читают утренняя рассылка, `notify-payment` и бот. Подмешаешь платёжку
  в `files` — она уйдёт в уведомление о новой заявке вместо счёта. Клиенту
  документ отправляется **вложением** (`sendDocument`) и **байтами, а не по
  ссылке**: клиент пересылает его поставщику, и при пересылке Telegram передаёт
  сам файл, а наша вечная публичная ссылка никуда не уходит; плюс имя файла в
  ссылке обезличено (кириллица схлопывается в `_`), а в сообщении оно должно
  быть человеческим. Счётчик `client_docs_notified` двигается только после
  успешной отправки — не дошло, допошлём при следующем касании.
- **Переписка по заявке — `payments.thread`, и в `toRow()` её быть не должно.**
  В переписку пишет и клиент — из кабинета и из бота, — поэтому отправлять её
  с фронта целиком нельзя ни при каких условиях: ответ, пришедший между
  15-секундными опросами, был бы затёрт. Пишется она только дописыванием на
  сервере: `post_staff_message` (сотрудник, автор из JWT) и `reply_by_token`
  (клиент по токену). По той же причине состояние «ждём ответа» не хранится
  колонкой — оно выводится из последнего сообщения (`threadState`).
  Файлы из ответа клиента попадают **во вложения заявки** и пересобирают зеркало
  `file_url`; статус при этом не меняется — «ждём ответа» это метка, а не статус.
- **Поле ввода не должно лежать внутри `#list`.** Он перерисовывается поллингом
  раз в 15 секунд, и набранный текст исчезает вместе с кареткой. Поэтому окна
  переписки (`#thBox`, `#clrBox`) лежат в `index.html` вне списка.
- `payments.last_edit_role` ставит триггер по JWT: `authenticated` — правил
  сотрудник, `anon` — клиент. От этого зависит, в какую сторону уйдёт
  уведомление о правке. Фронт это поле не пишет и писать не должен.
- Правки содержимого пишутся в журнал действием `EDIT` с парами «было → стало».
  Удаление — действием `DELETE` со **снимком всей строки** в `changes.deleted`:
  из него удалённую заявку можно восстановить (RUNBOOK 6.8).
- **Клиента и автора заявки (`client_id`, `created_by_staff`) меняет только
  админ** — это держит триггер `guard_payment_ownership`, а не RLS: политика
  описывает, кто может менять строку, а не что в ней менять нельзя. Без
  триггера бухгалтер из консоли браузера уводил заявку клиента в свои личные.
  Фронт эти колонки после создания заявки не пишет — и писать не должен:
  новый код, отправляющий их в `update`, упадёт у бухгалтера. Служебные пути
  (`service_role`, SQL Editor) не ограничены.
- **В боте всё, что написал человек, идёт через `esc()`** — получатель,
  реквизиты, назначение, имя файла, название фирмы. Сообщения уходят с
  `parse_mode: HTML`, и один `<` в названии получателя заставлял Telegram
  отвергнуть сообщение целиком: человек застревал на шаге без кнопок. `send()`
  и `answerCallback()` не бросают — `answerCallback` зовётся ДО обработки
  нажатия, и исключение в нём съедало само действие.
- **Фирма привязывается только к личному чату** (M5.2). В группе `chat.id` —
  все участники сразу: документы видел бы каждый, заявки заводил бы любой.
  `/start` вне `chat.type === "private"` отказывает до поиска по токену.
  Привязанные раньше группы не отвязывали — ищутся по `telegram_id < 0`.
  В `bind_test.sh` сообщения несут `chat.type`: без него бот теперь считает
  чат не личным.
- **Перепривязка фирмы к другому Telegram предупреждает прежнего владельца.**
  Не запрещаем (сменить телефон законно), но молча отвязывать нельзя — тот же
  класс, что инцидент «месяц без уведомлений». Сценарий в `bind_test.sh`.
- **`supabase-js` подключён с точной версией и `integrity`.** Обновляешь
  библиотеку — пересчитай хеш (команда в комментарии в `app/index.html`), иначе
  браузер заблокирует файл и приложение не загрузится ни у кого. Ссылка — на
  файл из пакета, не на голый адрес: тот jsdelivr минифицирует на лету.
- Личные задачи бухгалтера (`client_id is null`) видны только автору и админу.
- Экран «Клиенты» открыт и бухгалтеру (ради выгрузки в Excel), но заводить и
  удалять клиентов может только админ.
- **Поля заявки проверяет триггер `validate_payment_fields`**, а не RPC: сумма
  > 0, получатель 1–200 символов, реквизиты и назначение до 1000,
  периодичность `once/weekly/monthly`. Одна проверка на все двери — клиент,
  бот, форма сотрудника, копия повторяющегося. На UPDATE — только если менялось
  содержание, иначе старая кривая заявка перестала бы переводиться по статусам.
  Меняешь предел — правь и `maxlength` в форме, и `MAX_LEN` в боте.
- **Массовый UPDATE заявок выключает вебхуки на время записи.** `notify-client`
  срабатывает на любое обновление строки и «допосылает» всё, что не дошло
  раньше, — переписать служебную колонку во всех заявках клиента значит
  отправить ему пачку старых документов и вопросов. Образец —
  `update_client`: выключает триггеры на `supabase_functions.http_request`
  внутри той же транзакции и включает обратно. Проверяется
  `yellow_findings_test.sql` через очередь `net.http_request_queue`.
- **Название клиента меняется только через `update_client`** — `payments.client`
  хранит копию имени, и прямой `update clients set name` оставит старое имя во
  всех заявках.
- **Копия повторяющегося платежа несёт `parent_id`** — ссылку на оплаченную
  заявку. «Отменить оплату» удаляет копию по ней и только нетронутую (статус
  `new`, без правок, файлов и переписки — условие проверяет база в `delete`).
- **Дата, которую при правке не меняли, не переносится** (`edit_payment_by_token`).
  «Сегодня» после 17:00 при подаче переносится, как раньше, но форма клиента и
  бот говорят об этом заранее или сразу после.
- **Вопрос клиенту по закрытой (`sent`) заявке не задаётся** — ответить по ней
  клиент уже не может.
- Удалить клиента можно, **только если у него нет заявок**: `payments.client_id`
  стоит `ON DELETE SET NULL`, поэтому удаление «как есть» осиротит платежи —
  из очереди бухгалтера они пропадут совсем.
- Выгрузка в Excel собирается в браузере (`app/js/xlsx.js` — свой генератор
  без библиотек) из уже загруженной очереди, поэтому чужие данные в неё
  попасть не могут.

## Одна задача — одна сессия

Контекст забивает не переписка, а сама работа: тексты файлов, вывод команд,
скриншоты. В одной сессии за месяц накопилось 13 МБ, из них сообщения человека —
3%. Сжатие контекста теряет детали, и чем чаще оно срабатывает, тем выше риск,
что модель начнёт «помнить» несуществующее.

Поэтому: **закончил задачу → задеплоил → закоммитил → `/clear`.** Не ждать, пока
предложат сжатие посреди работы. Сессии привязаны к папке проекта, так что
история и память никуда не денутся; `/resume` вернёт старую беседу.

`/clear` ничего не теряет ровно при одном условии: всё важное уже записано —
сюда, в `docs/`, в тесты или в файл памяти. Если по ходу всплывает что-то, что
понадобится завтра, это надо **записать в файл, а не оставлять в чате**.

Что помогает не раздувать контекст по ходу:
- править файлы инструментом правки, а не `sed` в консоли — иначе система
  заново вкидывает в контекст **весь файл целиком**;
- вывод команд фильтровать (`| grep`, `| tail`), а не печатать целиком;
- скриншот делать один и в конце; где можно — измерять, а не разглядывать
  (`scrollWidth` вместо трёх снимков подряд);
- читать файлы кусками, а не целиком.

## Что не трогать

- `index.html` и `app.html` в корне — легаси прежних версий, не развиваются.
  Актуальный фронт целиком в `app/`.
- `HANDOFF.md`, `CONTEXT.md` — исторические записки, оставлены как есть.
