## Этап 0. Утёкший ключ — ✅ ЗАКРЫТО 09.09.2026, вечер

**Статус: подтверждено.** `raw.githubusercontent.com` отдаёт
`supabase/migrations/20260622000000_baseline.sql` без авторизации; в строках 275
и 279 — JWT с `"role":"service_role"`, `"ref":"gmvhphuabiyggfurfhmc"`, срок до
2036 года. В истории с коммита `8df37a3` (24.06.2026).

`service_role` обходит RLS целиком: все заявки, все токены клиентов, `auth`,
Storage мимо лимитов политики, любая RPC. Пока ключ жив, остальные пункты плана
смысла не имеют.

**Проверено 09.09 вечером:** ключ не просто лежит в репозитории — он **живой**.
`GET /rest/v1/clients` с ним отдаёт 200, то есть читает токены всех клиентов, а
по ним открываются их кабинеты.

**Найдено попутно, в отчёте этого нет:** те же триггеры создавались и при
локальном `supabase db reset` — стенд разработчика слал вебхуки боевым функциям
с боевым ключом. Убрано вместе с ключом.

**Сценарий — без простоя.** В проекте уже заведены новые ключи
(`sb_publishable_…`, `sb_secret_…`), подпись JWT переведена на ECC, а legacy
отключается кнопкой. Значит **ротировать JWT-секрет не нужно**: старые и новые
ключи работают параллельно, переводим по одному с проверкой на каждом шаге.

Подготовка — сделано:

- триггеры вебхуков убраны из `baseline.sql` (они и так живут вне миграций,
  `ARCHITECTURE.md` п. 5), вынесены в `scripts/webhooks.sql` с плейсхолдерами;
- chat_id бухгалтеров заменены плейсхолдерами (M11.8);
- функции читают `SB_SECRET_KEY` с откатом на `SUPABASE_SERVICE_ROLE_KEY` —
  работают и до отключения legacy, и после;
- `notify-client` и `notify-payment` проверяют `x-webhook-secret` (закрывает
  0.2), но **только если** `WEBHOOK_SECRET` задан — иначе проверка выключена,
  чтобы деплой можно было сделать до появления секрета в триггерах;
- `supabase/.temp/` в `.gitignore`, снимки `pgdelta` с ключом удалены с диска;
- CI-сторож `.github/workflows/secrets.yml`: JWT, `sb_secret_`, токен бота,
  `Bearer` в миграциях. Проверен в обе стороны — зелёный на текущем дереве,
  красный на старом `baseline.sql`;
- 190 pgTAP-тестов зелёные, локальные триггеры-вебхуки исчезли.

**Выполнено полностью.** Legacy-ключи отключены, утёкший service_role отдаёт
401 на всё — проверено четырьмя замерами (первый прошёл на кэше, поэтому
проверять надо не один раз). Уведомления, кабинет клиента и переписка живы,
ошибок в консоли нет. Подделка вебхука публичным ключом получает 403.

Порядок, которым это было сделано:

1. владелец присылает `sb_publishable_…` → правка `app/js/config.js`, пуш;
2. `supabase functions deploy notify-client notify-payment telegram-bot`;
3. владелец: `SB_SECRET_KEY` = `sb_secret_…` в Edge Functions → Secrets;
4. владелец: `scripts/webhooks.sql` в SQL Editor (подставив ключ и свой
   `openssl rand -hex 32`);
5. владелец: `WEBHOOK_SECRET` в Edge Functions → Secrets — защита включилась;
6. проверка сквозного сценария на тестовой фирме;
7. владелец: **Disable JWT-based API keys**;
8. проверка повторно + `curl` утёкшим ключом должен дать 401.

Через неделю: JWT Keys → Previously used → Revoke старому HS256.

**Из истории git ключ не вычистить** (форки, кэши сканеров). Спасает только то,
что старый ключ станет мёртвым.

**Проверка готовности:** старый ключ отвергается REST; заявка на тестовой фирме
проходит путь «вопрос → ответ → уведомление» целиком.

## Этап 2. Убрать общий `save()` — ✅ ЗАКРЫТО 10.09.2026

**Подтверждено фактом, а не чтением кода.** `node tools/racecheck.mjs`
воспроизводит гонку двух вкладок целиком и печатает обе половины:

```
Старое поведение (общий save):
  ✓ вторая вкладка отметила заявку оплаченной
  ✓ сталый upsert откатил статус обратно в «new» — так и терялась чужая работа

Новое поведение (точечный update с проверкой статуса):
  ✓ вкладка всё ещё показывает заявку новой (состояние сталое)
  ✓ после нажатия «Взять в работу» в базе по-прежнему «paid» — чужая отметка цела
  ✓ бухгалтеру сказали, что произошло
```

Первая половина и есть ответ на «а точно ли теряется»: да, теряется, проверено
на живом стенде. Скрипт остался в репозитории регрессом.

Что сделано вместо `save()` (правило записано в CLAUDE.md, раздел «Запись в
очередь — только точечная»):

- `changeStatusRemote(it, from, to)` — переход с условием
  `.eq("status", <что человек видел на экране>)`. Не совпало — перечитываем
  строку, обновляем экран и говорим человеку **(M1.1)**;
- `updateContentRemote(it)` — правка содержания **без статуса**: форма его не
  показывает и менять не должна **(M1.2)**;
- `attachDocRemote(it, from)` — документ бухгалтера с той же проверкой статуса;
- `insertPaymentRemote(rec)` — новая заявка одной строкой вместо upsert очереди;
- `removeRemote` теперь ждётся и проверяется: раньше ошибка удаления уходила
  молча в консоль, а строка пропадала с экрана.

Отсюда же закрылись **M4.8** (ложное «бухгалтер изменил» — оно возникало, когда
upsert возвращал в базу сталое содержание) и **M10.2** (такое затирание больше
не пишется в журнал как честная правка).

**M7.1 — закрыто в основной части.** Файл из ответа клиента больше не затирается
сменой статуса. Осталось честным компромиссом: правка содержания заменяет набор
файлов тем, что в форме, — то есть файл, приложенный клиентом при открытой
форме, всё ещё потеряется. Это уже осознанное действие одного человека, а не
побочный эффект всей очереди; окончательно лечится версией строки, и делать это
имеет смысл вместе с редизайном формы.

**Заодно закрыт M1.3 из этапа 3.** Копия повторяющегося платежа собиралась
клонированием заявки целиком и тащила за собой платёжный документ бухгалтера и
всю переписку по прошлому платежу. Теперь копия собирается по полям. Чинить это
отдельно позже было бы странно: код всё равно переписывался здесь.

Трогает `supabase.js`, `queue.js`, `main.js`; из `tools/uicheck.mjs` вынесен
общий стенд `tools/stand.mjs` — его же использует `racecheck.mjs`.
