# Карта модулей — для ревью по частям

Продукт разрезан на одиннадцать модулей, чтобы ревьюить по одному. Резали
**по швам продукта, а не по папкам**: модуль — это сквозной срез от таблицы до
кнопки, который делает одну вещь. Ревью «всех миграций» или «всего фронта»
пропускает баги на стыках слоёв — а они здесь самые дорогие.

Каждый модуль: что входит · что на кону · с чем граничит · чем покрыт.
Границы — самое важное: **баг на стыке не принадлежит ни одному модулю**, и
при ревью модуля его границы проверяются вместе с ним.

Порядок ниже — порядок ревью, по цене ошибки. Не по алфавиту.

Объёмы (строк) — чтобы планировать заходы: фронт 2 838, функции 1 075,
миграции 1 931, тестов 190 в 14 файлах.

## M1. Очередь бухгалтера и статусы ⚠ первым

Сердце системы. Здесь проводят деньги.

| | |
|---|---|
| Фронт | `queue.js` (351, кроме переписки) · `supabase.js` — `load/save/toRow/fromRow/updatePaymentRemote` · `state.js` · `utils.js` — `genId` (id копий повторяющихся платежей) · очередь в `index.html` |
| База | `payments` — статусы `new → in_progress → paid → sent`; `auto_created`, `created_by_staff`; миграции `20260724000007`, `20260724000008` |
| Тесты | `staff_created_test` (4), `staff_edit_test` (11) |
| Без тестов | вся логика фронта: `markPaid` / `undoPaid`, счётчики, фильтры |

**Что на кону.** `save()` делает **upsert всех заявок разом из локального
состояния** — «последняя запись побеждает». Две вкладки или два бухгалтера
одновременно — и одна из правок молча теряется. Повторяющийся платёж при
«оплачено» **создаёт копию на фронте**, а «отменить оплату» ищет и удаляет её по
совпадению полей — если совпало не то, удалится чужая заявка. Личные задачи
(`client_id is null`) видны автору и админу — и никому больше.

**Границы.** Каждая смена статуса — это UPDATE, который будит M4 (уведомления).
Файлы в строке — M3. Переписка в строке — M7. Кто видит какие строки — M6.

## M2. Заявка клиента: создание и правка

| | |
|---|---|
| Фронт | `main.js` — форма: `setFormMode`, `renderFormFiles`, `fillForm*`, `onSubmit`, `weekendDueBlocked` · `client_view.js` — `submitPaymentByToken`, `editPaymentByToken` · `dates.js` |
| База | `submit_payment`, `edit_payment_by_token`, `normalize_files`, `check_rate_limit`, `adjust_due_date`, `next_working_day`; миграции `baseline`, `…01_document_default_off`, `…03_edit_payment_by_token`, `…06_rate_limit`, `…09_working_days`, `…10_adjust_due_testable`, `…01_multi_files` |
| Тесты | `client_flow` (7), `rate_limit` (10), `working_days` (19), `multi_files` (13) |

**Что на кону.** Заявка с не той суммой, датой или файлом. Дата на выходной.
Правка после того, как бухгалтер уже взял в работу (гейт `status='new'`).
Правка чужой заявки по своему токену. Лимиты: 10/мин и 60/час на создание,
20/мин на правку — в базе, поэтому общие для веба и бота.

**Границы.** Один и тот же `submit_payment` зовут веб и бот (M5) — правило
меняется в одном месте для обоих. Даты на фронте (`isoLocal`, не
`toISOString`) обязаны совпадать с правилом в базе. Файлы — M3.

## M3. Файлы и документы

| | |
|---|---|
| Хранилище | бакет `files`: 10 МБ, белый список типов — миграция `…03_storage_limits`; политики Storage |
| База | `payments.files` + **зеркало `file_url`/`file_name` первого файла**; `staff_files` + `client_docs_notified`; миграции `…01_multi_files`, `…01_staff_documents` |
| Фронт | `supabase.js` — `uploadFile/uploadFiles`, `ALLOWED_EXT` · `queue.js` — `attachDocument`, `fileBadges`, `staffFileBadges` |
| Функции | бот — `uploadTelegramFile`, `MIME_BY_EXT` · `notify-client` — ветка 0, `sendDocument` байтами |
| Тесты | `storage_limits` (13), `multi_files` (13), `staff_documents` (9) |

**Что на кону.** Белый список типов живёт **в трёх местах** и обязан сходиться.
Зеркало `file_url` читают три потребителя — утренняя рассылка, `notify-payment`,
бот; не обновил — вложение молча пропало. Документ бухгалтера **отдельно** от
файлов клиента: смешать — платёжка уедет в уведомление о новой заявке как
«счёт от клиента». Ссылка на файл публичная и вечная, из Storage файл не
удаляется. Объём заливки ничем не ограничен (`SECURITY.md`, п. 7).

**Границы.** Файл из ответа клиента (M7) тоже ложится сюда и трогает зеркало.

## M4. Уведомления

| | |
|---|---|
| Функции | `notify-payment` (64) — INSERT · `notify-client` (307) — UPDATE: документ, статус, переписка, правки · `send_daily_reminder` — cron 8:30 Минск, исходник `supabase/daily_reminder.sql` |
| База | флаги `client_paid_notified`, `client_sent_notified`; счётчики `client_docs_notified`, `client_thread_notified`, `staff_thread_notified`; `last_edit_role` — миграции `…02_notify_once`, `…02_edit_tracking` |
| Вне кода | **DB Webhooks** настраиваются в панели Supabase; секреты `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` |
| Тесты | `staff_edit_test` — только `last_edit_role`. **Сами функции тестами не покрыты.** |

**Что на кону.** Потерять и продублировать одинаково плохо — на этом уже был
боевой инцидент (клиент месяц без уведомлений). Функция **сама обновляет строку**
после отправки → вебхук срабатывает снова: каждая ветка обязана на повторе
вернуть «skip», иначе цикл. Порядок веток жёсткий: документ, переписка, статус,
правки — `diffLines` про новые колонки не знает. Направление уведомления о
правке решает `last_edit_role`, который ставит триггер по JWT.
`send_daily_reminder` в проде хранит **боевой токен в теле** — в репозитории
плейсхолдер (см. M11).

**Границы.** Будится всем, что пишет в `payments`: M1, M2, M3, M7. Знает про
несколько фирм на одном чате (`firmSuffix`) — M5.

## M5. Telegram-бот

| | |
|---|---|
| Функция | `telegram-bot/index.ts` (608): привязка `/start`, `/payments`, диалог `/new`, `/cancel`, ответ на вопрос |
| База | `tg_sessions`; `clients.telegram_id` — **не уникален**; миграции `…11_rotate_unbinds_telegram`, `…01_shared_telegram` |
| Вне кода | вебхук Telegram, секрет `TG_WEBHOOK_SECRET`; JWT у функции **выключен** |
| Тесты | `bind_test.sh` (вручную, против локальной функции), `delete_client_test` (17, часть про фирмы), `rotate_token_test` (11) |

**Что на кону.** Один аккаунт — несколько фирм: `/start` **не снимает** прежние
привязки (снимал — был инцидент), а диалог `/new` требует ровно одной фирмы,
иначе заявка уйдёт не туда. `.maybeSingle()` по `telegram_id` запрещён.
Бот ходит под `service_role` — **RLS его не останавливает**, все проверки
принадлежности он делает сам (чужой id в `callback_data`). Сессия диалога
переживает дни: старая кнопка, старый черновик.

**Границы.** Заявку создаёт через `submit_payment` (M2), файл грузит по правилам
M3, ответ шлёт через `reply_by_token` (M7).

## M6. Доступ, роли и безопасность

| | |
|---|---|
| Фронт | `auth.js` (79) — вход, роль из `staff` |
| База | `staff`, `is_admin`; RLS: `pay_staff_*`, `clients_*`, `staff_*`; токен клиента — `client_by_token`, `rotate_client_token`; `revoke` служебных RPC — `…02_lock_admin_rpc` |
| Документ | `SECURITY.md` |
| Тесты | `security_surface` (21), `rpc_and_rls` (14), `rotate_token` (11) |

**Что на кону.** Новая функция в Postgres **по умолчанию открыта PUBLIC и anon**
— `grant` ничего не ограничивает, ограничивает только `revoke`. Так однажды
оказался открыт журнал. Бухгалтер видит только своих клиентов, админ — всех.
Токен в URL — единственный ключ клиента; перевыпуск делает старый мёртвым и
**сбрасывает привязку к боту**.

**Границы.** Каждая новая RPC в любом модуле проходит через `security_surface_test`.

## M7. Переписка по заявке (сквозной, ревьюить после M1–M5)

| | |
|---|---|
| База | `payments.thread`, счётчики; `post_staff_message` (invoker, автор из JWT), `reply_by_token` — миграция `…01_payment_thread` |
| Фронт | `thread.js` (180) · `queue.js` — метки, `remindClient` · `client_view.js` — окно ответа · `index.html` — `#thBox`, `#clrBox` |
| Функции | `notify-client` — ветка 0.5 · бот — кнопка `reply:`, шаг `reply`, TTL 12 ч |
| Тесты | `thread_test` (28) |

**Что на кону.** `thread` **не входит в `toRow()`** — иначе общий `save()` из M1
затрёт ответ клиента. Файл из ответа идёт во вложения и трогает зеркало (M3).
Границы анонимной записи: 1000 символов, 10 файлов, 100 сообщений, 20/мин.
Закрытая заявка (`sent`) ответов не принимает.

**Границы.** Это модуль-стык: он касается M1, M3, M4, M5 одновременно — потому и
ревьюится после них, когда их правила уже свежи в голове.

## M8. Кабинет клиента

| | |
|---|---|
| Фронт | `client_view.js` (332) — рендер, шаги, поиск и фильтры · `main.js` — поллинг 15 с, `switchView` для режима токена · `config.js` — прод/локаль по hostname |
| База | `list_payments_by_token` (`SETOF payments` — новые колонки приезжают сами), `client_by_token` |
| Тесты | фронт — нет; RPC — в `rpc_and_rls` |

**Что на кону.** Клиент видит только своё — держится на одной RPC. Статус на
карточке обязан совпадать с тем, что бухгалтер видит в очереди. **`#list`
переписывается поллингом раз в 15 секунд** — ничего с вводом внутри него быть
не может. Фильтруется на рендере, `state.items` не мутируется.

**Границы.** Правка заявки отсюда — M2, ответ бухгалтеру — M7.

## M9. Клиенты, администрирование, выгрузка

| | |
|---|---|
| Фронт | `clients.js` (138) — список, добавление, ссылка, перевыпуск, удаление · `export.js` (77) + `xlsx.js` (260) — **собственный генератор XLSX без библиотек** |
| База | `delete_client` — только без заявок (`client_id` стоит `ON DELETE SET NULL`); миграции `…01_delete_client`, `…01_shared_telegram` |
| Тесты | `delete_client_test` (17); генератор XLSX — нет |

**Что на кону.** Удаление клиента с заявками осиротит их — из очереди они
пропадут совсем. Выгрузка собирается из уже загруженной очереди, поэтому чужие
данные в неё не попадают — но сам формат XLSX написан руками: битый файл
Excel откроет с ошибкой, а не пожалуется.

**Границы.** Экран открыт и бухгалтеру ради выгрузки — заводить и удалять может
только админ (M6).

## M10. Журнал изменений

| | |
|---|---|
| База | `payments_audit`; триггеры `log_payment_change`, `stamp_payment_editor`; `payment_content_changed` — одно определение «что считается правкой» на оба; миграции `…04_audit_log`, `…02_edit_tracking` |
| Тесты | `audit_log_test` (13), `staff_edit_test` (11) |

**Что на кону.** Правка суммы оплаченного платежа без следа. Служебные поля
(флаги уведомлений, переписка) **не должны** считаться правкой — иначе журнал
засорён, а клиенту уходит ложное «бухгалтер изменил заявку». Триггерным функциям
права намеренно не трогают: ошибка там уронит вставку заявок.

## M11. Инфраструктура и эксплуатация

| | |
|---|---|
| Репозиторий | `supabase/config.toml` (порты 183xx), `seed.sql`, дисциплина миграций (`CLAUDE.md`) |
| CI | `test.yml` — pgTAP на каждый push · `backup.yml` — шифрованный дамп 05:00 Минск · `health.yml` — каждые 15 минут |
| Вне кода | секреты функций, DB Webhooks, учётки в Auth, **боевой токен внутри `send_daily_reminder`** |
| Инструменты | `tools/uicheck.mjs` — снимки и ошибки консоли; `docs/RUNBOOK.md` |
| Легаси, не ревьюить | `supabase/telegram_bot.sql`, `telegram_sessions.sql` — «выполнить в SQL Editor», эпоха до миграций; `index.html` и `app.html` в корне |

**Что на кону.** Baseline-миграция содержит **плейсхолдер токена** — прогнать её
на проде значит сломать утреннюю рассылку; она помечена применённой через
`migration repair`. Бэкап **не включает `auth.users`** — учётки сотрудников
восстанавливаются руками. Порядок выкладки: миграция → функции → фронт, обратный
ломает живых клиентов. Нет staging. Фронт летит на прод с любым `git push`.

## Как этим пользоваться

Один заход — один модуль, вместе с его границами. Перед заходом прочитать
строку «Что на кону» и файл «как задумано» для роли (`docs/client.md`,
`accountant.md`, `admin.md`). Формат находок и правила работы с продом —
`docs/REVIEW-BRIEF.md`.

Где тестов нет — там глазами и стендом: весь фронт, `notify-*`, генератор XLSX.
