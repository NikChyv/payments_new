# Бриф на проверку продукта

Стартовый пакет для того, кто проверяет систему свежим взглядом. Цель — найти
**расхождения между тем, как система себя ведёт, и тем, как задумано**: баг это
не только падение, но и «работает не так, как обещано человеку».

Читается целиком перед началом. Дальше — по ссылкам.

---

## 1. Что за продукт

Сервис для бухгалтерской аутсорсинговой компании. Клиент по персональной ссылке
или в Telegram-боте оставляет заявку на платёж; бухгалтер ведёт единую очередь
по срокам, проводит платежи и возвращает клиенту платёжный документ.

**Система живая**: ей прямо сейчас пользуются реальные клиенты и два бухгалтера.
Цена ошибки — потерянное или продублированное платёжное поручение.

Четыре роли: **клиент по ссылке**, **клиент в боте**, **бухгалтер**, **админ**.

## 2. Что прочитать перед началом

По порядку, это быстро:

| Файл | Зачем |
|---|---|
| `docs/ARCHITECTURE.md` | как устроено: таблицы, RPC, функции, потоки |
| `docs/MODULES.md` | карта модулей: что входит, что на кону, границы — **ревью идёт по ней, по одному модулю за заход** |
| `docs/client.md` | **как задумано** для клиента |
| `docs/accountant.md` | **как задумано** для бухгалтера |
| `docs/admin.md` | **как задумано** для админа |
| `SECURITY.md` | модель угроз и что уже закрыто |
| `CLAUDE.md` | грабли проекта и правила работы с ним |

Три файла «как задумано» — главные. Без них найдутся только падения, а расхождения
с замыслом пройдут мимо: непонятно, что считать правильным поведением.

## 3. Стенд

Полная копия бэкенда поднимается локально. **Ломать здесь можно всё.**

```
supabase start                    # стек (порты 183xx)
supabase db reset                 # схема с нуля + демо-данные
supabase test db                  # 190 pgTAP-тестов, должны быть зелёными
node tools/uicheck.mjs --serve    # поднять фронт и держать открытым
```

Последняя команда сама заводит локальную учётку бухгалтера и печатает адреса:
кабинет клиента с готовым токеном, экран входа, логин и пароль. Демо-клиенты —
`demotoken1` и `demotoken2` (см. `supabase/seed.sql`).

Ещё две команды, которые пригодятся:

```
node tools/uicheck.mjs              # снимки экранов + ошибки консоли
node tools/uicheck.mjs --width 390  # то же на мобильной ширине
```

Скрипт показывает и то, чего не видно глазами: молчаливые ошибки в модулях
(страница просто остаётся пустой) и элементы, вылезающие за край окна.

**Известное на сегодня, искать не надо:** на 390 px экраны бухгалтера уезжают
вбок (`#tabs`, `#staffBox`) — заведено в `docs/REDESIGN.md`.

## 4. Чего локальный стенд не покрывает

**Telegram-бот локально не работает** — ему нужен публичный вебхук. Локально
можно гонять только `supabase/functions/telegram-bot/bind_test.sh` (привязка
`/start`, инструкция в шапке файла).

Значит все сценарии бота проверяются **на проде, через тестовую фирму**. Доступы
к ней в репозитории не лежат — спросить у владельца.

## 5. Правила работы с продом

Нарушение любого из трёх пунктов заметят живые люди.

1. **Прод — только на чтение**, кроме тестовой фирмы. Не менять чужие заявки, не
   переключать статусы, не трогать клиентов.
2. **Любое действие шлёт настоящие уведомления.** Оплата статуса — клиенту в
   Telegram. Ответ клиента — **в общий чат обоих бухгалтеров**. Тестовая фирма от
   этого не спасает: чат бухгалтеров общий. Проверяешь бота — предупреди их, что
   сегодня будет мусор.
3. **Ничего не выкатывать.** Не `db push`, не `functions deploy`, не `git push`.
   Порядок выкладки жёсткий, и нарушение ломает работу живым клиентам.

Тестовые заявки на проде заводить с `auto_created = true` — иначе уведомление о
выдуманном платеже уйдёт бухгалтерам.

## 6. Что пройти

Не «покликать», а пройти каждую роль целиком, сверяясь с файлом «как задумано».

**Клиент по ссылке:** открыть кабинет · завести заявку со всеми полями и без
необязательных · приложить файлы · отредактировать заявку, пока она новая ·
повторить старую заявку · поиск и три фильтра · ответить на вопрос бухгалтера
текстом и файлом · получить платёжный документ.

**Клиент в боте:** привязка по ссылке · `/payments` · `/new` целиком · `/cancel`
посередине · ответ на вопрос по кнопке · один аккаунт с несколькими фирмами.

**Бухгалтер:** вход · очередь, счётчики и фильтры · взять в работу, оплатить,
вернуть назад · правка чужой заявки · дубликат · удаление · приложить документ ·
задать вопрос клиенту и напомнить · выгрузка в Excel · личные задачи.

**Админ:** завести клиента · выдать ссылку · перевыпустить токен · удалить
клиента · увидеть чужих клиентов и убедиться, что бухгалтер их не видит.

**По краям — отдельным заходом.** Пустые и очень длинные значения; ноль и
отрицательные суммы; даты в прошлом, на выходных и в нерабочее время; файлы не
того типа и больше 10 МБ; двойные клики; кнопки не в том порядке; две вкладки
одновременно; обрыв сети посередине действия; открыть чужую ссылку.

## 7. Где ошибка дороже всего

Это границы системы, а не подсказки, где искать:

- **суммы и даты** — рабочий график пн–пт до 17:00 живёт в базе и действует
  одинаково в вебе и в боте;
- **уведомления** — потерять и продублировать одинаково плохо;
- **несколько фирм на одном Telegram-аккаунте** — самое хрупкое место бота;
- **чужие данные** — бухгалтер видит только своих клиентов, клиент только свои
  заявки, личные задачи бухгалтера видны автору и админу;
- **файлы** — типы, размер, и то, что первый файл заявки зеркалится в поля,
  которые читают сразу три места.

## 8. Как оформлять находки

Каждую **воспроизвести дважды** и записать так:

```
Что делал:     шаги, по которым это повторяется
Что ожидал:    и почему — со ссылкой на файл «как задумано»
Что получилось:фактическое поведение
Чем грозит:    кто пострадает и насколько
Где:           файл и строка, если нашлось в коде
```

Разложить на три кучи: **сломано** · **неудобно** · **хотелки**. Чинится сначала
первая, целиком.

Подозрения без воспроизведения не приносить — их разбор стоит дороже, чем сама
проверка. Если воспроизвести не удалось, так и написать: «видел один раз,
повторить не смог».

## 9. Чего не делать

- **Не чинить по ходу.** Сначала найти всё, потом чинить отдельным заходом:
  иначе день уйдёт на косметику, а платёжный баг останется ненайденным.
- **Не предлагать улучшений, пока не закончен поиск поломок.** Хотелки в третью
  кучу, они не должны разбавлять отчёт.
- **Не переписывать архитектуру.** Фронт намеренно ванильный, без сборки и npm;
  «давайте на React» — это не находка.
- **Не трогать `index.html` и `app.html` в корне репозитория** — легаси прежних
  версий, не развивается. Актуальный фронт целиком в `app/`.
